# doodle_shooter — 白纸 + 铅笔涂鸦 横版飞机射击

纯 C99 单文件实现，零外部资源（无图片文件、无字体文件、无音频）。
所有美术资源在代码内用字符画生成，所有随机数/计时/物理积分手写，
两个图形后端（Win32 GDI / X11）在同一文件内按平台自动选择。

---

## 一、编译与运行

### 方式 A：Visual Studio（推荐，双击即用）

直接双击 **`doodle_shooter.sln`**，在 VS 里选好配置后按 `F5`（调试）或 `Ctrl+F5`（运行）。

解决方案含两个工程：

| 工程 | 子系统 | 用途 |
|---|---|---|
| `doodle_shooter` | Windows | 图形窗口版，F5 直接玩 |
| `doodle_tools` | Console | 命令行工具版，跑 `--selftest` / `--sim` / `--preview` |

支持 `Debug|Release` × `Win32|x64` 四种配置，产物落在 VS 默认目录：

```
x64\Release\doodle_shooter.exe     x64\Debug\doodle_shooter.exe
Release\doodle_shooter.exe          Debug\doodle_shooter.exe
```

工程已配好：`/W4` 警告级别、`/TC` 强制 C 编译、`/utf-8` 源码编码（源文件含中文注释，
不加会报 C4819）、`/O2` 优化、`/MT` 静态运行库，平台工具集用 `$(DefaultPlatformToolset)`
自动匹配已安装版本（VS2019→v142 / VS2022→v143 / VS2026→v145 均可）。

> **命令行构建**（不开 IDE）：
> ```bat
> msbuild doodle_shooter.sln /p:Configuration=Release /p:Platform=x64 /t:Rebuild
> ```
> 或直接跑仓库里的 `build_msvc.bat`（自动定位 SDK 并顺带跑一遍自检）。

### 方式 B：MinGW (gcc)

```bash
gcc -O2 -Wall -Wextra -mwindows -o game.exe game.c -lgdi32 -luser32
gcc -O2 -Wall -Wextra -std=c99 -o game_console.exe game.c -lgdi32 -luser32
```

### 方式 C：Linux / macOS (X11)

```bash
gcc -O2 -Wall -Wextra -o game game.c -lX11 -lm
```

所有方式编译结果均为**零警告**（gcc `-Wall -Wextra` / MSVC `/W4`）。

### 运行模式
```bash
game                # 正常游戏
game --selftest     # 断言自测：精灵尺寸 / 碰撞边界 / 难度曲线 / 容量上限
game --sim          # 无头模拟 20 局 × 1800 帧，随机输入，检查不崩溃不越界
game --preview      # 打印字符画与点阵字预览（不依赖显示设备）
```

> 工具版（Console 子系统）才有控制台输出。窗口版（Windows 子系统）若带参数运行，
> 程序会自动附加到父控制台，输出同样可见。

## 三、美术风格是怎么做出来的

- **纸 + 墨**：底色 `#F7F7F3` 纸白，线条 `#111111` 墨黑，体积感只用
  `#E4E4E4 / #B4B4B4 / #6E6E6E` 三级灰阶。调色板按亮度**严格递增**排列，
  自检会断言这一点，淡出时沿这个阶梯回退到纸色，因此永远不会出现彩色或渐变。

- **歪的直线**（`stroke_jitter`）：沿线段取样点，在**法线方向**叠加
  「正弦微弯 + 每点随机扰动」，再以约 7% 概率在某点断开笔迹（断墨）。

- **歪的圆**（`circle_sketch`）：画两段**不闭合**的弧，各自起始角随机，
  弧上半径再做随机起伏 —— 所以同一个圆每帧形状都不同，像手绘的。

- **铅笔毛边**（`sprite_blit`）：精灵每个像素在绘制时有 1/9 概率整体偏移
  ±1px，形成描边的粗糙感。为控制绘制调用数，同色且同偏移的连续像素
  会合并成一条横带一次性填充。

- **手绘云**：每朵云由 5 个抖动圆拼接，缓慢上飘 + 轻微左移，越界后回卷。

## 四、玩法与参数

| 项目 | 数值 |
|---|---|
| 玩家飞机 | 13×18 字符画，机头白 / 机身灰 / 尾焰，3 倍放大 |
| 敌机 | 17×13 字符画（纸飞镖，机头朝左），3 倍放大；每 6 只出 1 只 4 倍的「干扰机」 |
| 移动 | 加速度 0.62，摩擦 0.85（惯性），左右移动时机身 1px 侧倾 |
| 射击 | 自动，每 7 帧一发，5×9 胶囊形（2 倍放大）+ 极短尾迹 |
| 生成间隔 | `diff/(diff+35)` 平滑函数，从 0.95s 收敛到 0.26s |
| 敌机速度 | 随时间轻微提升，上限 2.90 |
| 碰撞 | 圆-矩形近似判定；玩家开场 80 帧无敌（闪烁） |
| 击毁 | 8~16 个随机旋转碎屑 + 3 层不同半径、迅速扩散又淡出的铅笔圈 |
| 受击 | 震屏 8 帧，碎屑飞散，2 秒后空格重开 |
| 状态机 | 0 标题（飞机悬停 + 闪烁 PRESS SPACE）→ 1 游戏中 → 2 失败 |
| HUD | 左上分数，右上最高分（本次运行内保留） |

## 五、代码约束的落实方式

| 约束 | 实现 |
|---|---|
| 单文件、≤900 行 | `game.c` 887 行，单文件 |
| 只用 C99 标准库 + 一个图形后端 | 仅 `stdio/stdlib/string/math/stddef/time` + 平台图形 API |
| 禁止游戏引擎/外部资源 | 无任何 `load`/文件读取；美术全部由 `char*` 字符画生成 |
| 逐像素放大绘制 | Win32 用 `FillRect`/`Polyline`/`SetPixel`，X11 用 `XFillRectangle`/`XDrawLines` |
| 随机/计时/积分自写 | xorshift32 双流（逻辑流 / 美术流分离）、`QueryPerformanceCounter` 或 `clock_gettime` |
| 固定步长 ~60FPS | `now_ms()` + `sleep_ms()` 补偿，主循环固定 1/60 步 |
| 零 malloc 循环、静态容量 + used 标记 | 全部实体为静态数组 + `alive` 标记；游戏内零动态分配 |
| 一次编译通过、零 warning | `-Wall -Wextra` 实测无输出 |

**随机双流**是这里的关键设计：画面抖动用独立的 `g_rng_art`，
玩法用 `g_rng_game`，所以画面的随机毛边不会让同一局玩法的手感漂移。

## 六、自检覆盖了什么

`--selftest` 共 832 条断言（覆盖精灵/字体/调色板/碰撞/难度/容量/淡出/按键八类）：

1. 精灵字符画每行宽度必须严格等于声明值（13 / 17 / 5）
2. 点阵字表长度与字符集长度一致（43）
3. 调色板亮度严格递增（素描层次不被破坏）
4. 圆-矩形碰撞的四种边界情形（内 / 外 / 贴边 / 越界）
5. 难度曲线从 0.95s 起、单调递减、恒 ≥ 0.26s
6. 反复生成 5000 次后实体数仍不超容量上限
7. 灰阶淡出索引恒在合法范围
8. **按键映射完整性**：五个逻辑键都能被内部码和 Win32 虚拟键码触发，
   未知码必须被拒绝（这条断言是下面「已修复的两个 Bug」的护栏）

`--sim` 用随机输入跑 20 局 × 1800 帧，检查玩家坐标不越界、分数非负，
并报告真实死亡次数（用于确认碰撞逻辑确实生效，而不是"永远不会死"）。

## 七、已修复的两个真实 Bug（都是"编译通过但跑不对"）

这两个坑值得单独记下来，因为它们**都不会触发任何编译错误或警告**：

### Bug 1：窗口一片空白

**症状**：窗口正常弹出、标题栏正常，但客户区纯白，什么都没有。

**根因**：三处叠加。

| # | 问题 | 后果 |
|---|---|---|
| 1 | `gfx_poll()` 用 `PeekMessage(PM_REMOVE)` 取出消息后，非按键消息直接 `continue` 丢弃 | `WM_PAINT` 从未到达窗口过程，绘制区域永不被验证 |
| 2 | `gfx_present()` 用 `GetDC + BitBlt` 直接往窗口画 | 绕过 `BeginPaint/EndPaint`，在 DWM 合成下内容不会被真正提交到屏幕 |
| 3 | 窗口过程虽然处理了 `WM_PAINT` | 但永远收不到消息 |

**修法**：`gfx_present()` 改为 `InvalidateRect + UpdateWindow`，让 `WM_PAINT`
走正规重绘路径（`BeginPaint` → `BitBlt` → `EndPaint`）；`gfx_poll()` 对非按键
消息调用 `TranslateMessage + DispatchMessageA`，保证消息真正派发给窗口过程。

### Bug 2：键盘完全无响应

**症状**：画面正常，但按空格没反应、方向键不动。

**根因**：`key_lookup()` 期望的是内部键码（`KEY_L = 256`），
而 Win32 后端直接把虚拟键码（`VK_LEFT = 37`）传了进去 —— 表全部查不中，
`key_lookup` 一律返回 `-1`，所有按键被静默丢弃。

**修法**：在 `key_lookup` 内加一段 `#ifdef _WIN32`，把 `VK_*` 归一到逻辑键。
两个后端从此共用同一张逻辑键表。

### 为什么值得写下来

上面两个 bug **都无法用"编译通过 + 零警告 + 断言全绿"发现**——
因为它们都是"运行时链路断裂"，不是"代码写错"。

真正抓到它们的是**从真实屏幕抓取像素**并统计"墨色 vs 纯白"像素数：

```
修复前: pure_white=306198  ink=1944    ->  屏幕空白
修复后: pure_white=63      ink=19003   ->  画面正常
```

这个手法（DPI 感知抓屏 + 像素分类统计）已固化为 `_cap2` 探针的思路，
是本项目里最有效的验收手段 —— 它看的是**用户眼睛看到的东西**，
而不是内存里那份"看起来对"的副本。
